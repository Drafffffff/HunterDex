# HunterDex 0.3 体验重构方案

日期：2026-09-29。状态：方案与基线调查，尚未修改应用行为。

目标：用户可以流畅地用中文找武器，直接比较斩味和数值，沿清晰的生产／强化路线查素材与任务，再回到原来的位置。

## 1. 现状判断与证据

当前版本是通用目录框架。武器这种以派生关系为核心的数据被塞进通用详情页，搜索、选择、导航又共用同一刷新流程。需要重构交互与状态，不能只改颜色和间距。

已确认的实现问题：

- Store.swift 中 search.didSet 在 MainActor 同步执行 refresh，每次输入都遍历 22,637 个目录条目；匹配项每次拼接 searchText，并做本地化字符串匹配。筛选条件也各自触发刷新，没有合并提交。
- 名称排序在每次查询后重复执行。分类数量和武器筛选选项也在视图读取时重新遍历目录。
- 选择条目会同步读取详情；武器详情会重新查询整棵派生树。导航可能清除搜索与筛选，然后再次触发多次 refresh。
- 详情使用 .id(detail.entry.id)，跳转时整个详情视图重建。树节点、详情行每次获得新的 UUID，展开状态与滚动上下文难以保持。
- 武器树嵌在详情内，高度最多 300；深层节点通过缩进表达，缺少连续连线。点击虽已有处理函数，但跳转后的上下文容易丢失，不能据此称为可用的树导航。
- 列表的 Entry 不包含斩味、属性、会心与插槽，当前只能逐件进入详情比较。
- 现有 7 组自检验证数据和功能结果，没有输入延迟、中文输入法、滚动流畅度或导航上下文的验收。

本机优化编译下，直接调用现有 Store、每组 8 次的测量：

| 场景 | 中位数 | 最大值 |
|---|---:|---:|
| 武器搜索「火龙」，图鉴排序 | 35.2 ms | 35.7 ms |
| 武器搜索不存在的名称 | 36.0 ms | 36.2 ms |
| 武器搜索 r，8,277 个结果 | 27.7 ms | 28.4 ms |
| 武器空查询，名称排序 | 76.7 ms | 121.6 ms |

这些数字只测筛选／排序，不包含 SwiftUI 差异计算、布局、图像解码和实际输入法交互，不能当作端到端延迟。本轮简单英文输入未复现持续卡死；主线程负担已经证实，持续卡死的具体触发链仍需现场采样。诊断源与原始输出在 .cache/diagnostics/。

## 2. 搜索：输入不受查询拖累

交互规则：

1. 输入框立即响应。中文拼音组词期间保留候选状态，不把未提交的拼音反复送进正式搜索；提交汉字后再搜索。
2. 提交文字后约 120 ms 合并连续输入；回车直接执行，清空搜索立即恢复已缓存目录。
3. 新查询取消旧查询，同时用请求序号拒绝过期结果。输入「火」再输入「火龙」后，「火」的慢结果不能覆盖新结果。
4. 搜索过程中保留上一批结果；仅当超过约 150 ms 才显示轻量状态提示，不把列表清空成白屏，不每次都闪加载动画。
5. 搜索不自动打开第一项，不自动滚动详情，不改变输入焦点。方向键选结果，回车进入；退出搜索可以恢复此前浏览位置。
6. 搜索范围始终写清楚，例如「搜索大剑」。附近提供「全部武器」范围切换；跨类别检索是独立入口，不能暗中改变范围。
7. 无结果时显示当前类型和筛选条件，提供清除筛选、扩大搜索范围操作。不能把“无中文译名”伪装成“没有此物品”。

实现方案：

- SearchIndex 保存不可变、预先规范化的中文／英文／已核实别名／编号字段，并按分类及武器类型建立候选集。索引构建完成后复用。
- 查询与排序在专用后台执行器执行。查询返回稳定条目 ID，主线程只应用必要的 UI 状态变化。
- 分类计数、类型列表、稳定排序结果缓存；搜索索引不因收藏、详情切换而重建。
- 先以这 2.3 万条数据实现轻量内存索引，避免引入尚未需要的复杂数据库搜索体系。只有实测不达标再升级全文／子串索引；中文检索必须有独立验证。
- 列表只创建可见行及少量预取行。首批可展示约 200 条，再渐进加载；明确显示完整结果总数，不能静默截断。排序必须针对完整结果集合。
- 图片读取、解码与数据库详情查询离开主线程，使用有上限的缓存。数据库连接由专用 actor／串行执行器拥有，不能直接跨线程共享当前连接。
- 中文输入的组合态必要时通过 AppKit 搜索控件桥接，以 marked text 状态测试实际行为。

定位与回归必须包含：连续输入、连续删除、粘贴、中文输入法选词、零结果、8,000+ 结果、搜索时切分类、搜索时点击旧结果、后台慢查询晚返回。

## 3. 武器使用独立的工作界面

保留原生窗口与侧栏，把“武器”展开为 14 个固定顺序的种类：大剑、太刀、片手剑、双剑、大锤、狩猎笛、长枪、铳枪、斩击斧、盾斧、操虫棍、弓、轻弩、重弩。

默认恢复上次使用的种类，首次进入选择大剑；取消一进入便混排 10,877 条武器等级的默认状态。每种武器分别记住筛选、排序、选中节点与滚动位置。

建议布局（示意，不是实际数据）：

```text
┌──────────────┬────────────────────────────────────┬──────────────────────┐
│ 图鉴         │ 大剑   [搜索大剑…]                 │ 当前武器 · Lv.3      │
│ 武器         │ [派生树 | 性能列表]  斩味 [通常 ▾] │ 攻击 / 属性 / 会心   │
│   大剑       │ [属性 ▾] [稀有度 ▾] [最终强化]     │ 插槽 / 稀有度        │
│   太刀       ├────────────────────────────────────┤                      │
│   片手剑     │ 名称          攻击 属性 会心 斩味  │ 从上一级强化         │
│   …          │ ▼ 某武器 Lv.1  …    …   …   ▰▰▰   │ 材料 A ×2   →        │
│ 防具         │ └─ 某武器 Lv.2 …    …   …   ▰▰▰   │ 材料 B ×3   →        │
│ 道具与素材   │    ├─ 某武器 Lv.3 [当前选中]       │ 强化费用             │
│ 怪物         │    └─ 分支武器 Lv.1                │                      │

│ 收藏         │                                    │ 分支 C / 分支 D  →   │
```

中间是主要操作区，右侧是可收起的检查器。减少大标题、巨型数字卡片与重复类别图标，把空间交给可比较的信息。使用 macOS 系统字体、原生键盘操作、可调整列宽、清晰的选中与焦点状态；斩味颜色用于表达游戏数据，强调色只标识选择和链接。

窗口变窄时允许收起全局侧栏和详情检查器，保留名称、攻击与斩味主列；其他字段可配置显示。长名称允许两行并有完整提示，不能只剩省略号。右侧检查器与树表分别滚动，不再把小树塞进详情滚动页里。

技术选择：SwiftUI 保留窗口、工具栏和一般详情；武器树表优先用 NSOutlineView，性能列表优先用 NSTableView，通过桥接接入。目的是获得成熟的行复用、层级展开、表头排序和键盘导航。最终仍需用真实数据证明流畅，不能把换控件当成性能保证。

## 4. 派生树：能看懂路线，也能稳定跳转

数据快照含 787 棵独立根树，单树最大 186 个节点、最大深度 17；当前父子边没有跨武器类型。按类型组织后，每类约 43–67 棵根树。没有必要一次铺开所有树。

两种视图使用相同节点 ID 与选择状态：

- 派生树：默认浏览方式。按生产起点分组，清楚区分根节点、强化边、分支和最终强化。只展开当前路线与必要邻接分支，其余可以逐组展开。
- 性能列表：用于筛选和排序比较。支持攻击、属性、会心、插槽、稀有度、最高斩味等字段。点击「定位派生树」回到该节点的真实位置。

必须遵守的树交互：

1. 单击节点更新右侧详情，树的位置和展开状态不变。再次点击当前节点不重新加载整页。
2. 点击分支／上一级链接，选中对应真实节点，并只展开到达它所需的祖先。只有目标在可视范围外时才最小幅度滚动，不每次强制居中。
3. 当前节点、起点到当前的路径、当前之后可达的分支有明确层次。连线不能靠重复的转弯箭头暗示关系。
4. 搜索树时保留匹配节点的祖先，匹配项高亮、上下文项弱化；不把祖先算成搜索命中数。清空搜索恢复原展开状态。
5. 「仅最终强化」在列表中只显示终点；在树中保留必要的前置节点，明确它们只是路径上下文。
6. 树表不按攻击力重新排列父子节点；需要排序比较时切换性能列表，避免破坏路线语义。
7. 生产与强化明确分开。某个中途节点如果可直接生产，也应标识“可直接生产”；不能假设只有根节点能生产。
8. 键盘上下选择，左右展开／收起，回车查看；节点名称、层级和状态提供可访问性标签。

浏览历史保存完整上下文：页面类型、武器类型、搜索与筛选、选中节点、树展开集合、滚动锚点。点击素材再后退必须回到同一棵树、同一节点、同一位置。普通方向键移动不把历史刷满；跨页面访问和明确的路线跳转才记录有意义的历史。

数据层建立稳定 WeaponNode / WeaponTree 索引，用原始 ID、parent_id 与实际组件记录建图，不能按名称或数字等级猜派生关系。结构与详情分别缓存；检验缺失父节点、循环、孤立节点和可直接生产节点。必要的行 ID 使用稳定复合键，停止为每次读取产生新 UUID。

## 5. 斩味进入每一行，而不是藏在详情

近战武器表行的固定信息：名称与等级、攻击、属性／异常、会心、插槽、斩味；稀有度可作为小标签或可选列。

斩味列：

- 每行绘制真正的红橙黄绿蓝白紫分段条，提供足够的固定列宽和对比度，白斩在浅色模式下有边界。
- 顶部统一切换「通常／匠 +1／匠 +2」，整张表跟随，列头始终显示当前条件。比较双方采用相同条件。
- 列表所有武器使用同一个斩味总尺度；当前每件武器各自归一化的方式不能搬进横向比较，否则长度会误导。
- 右侧详情同时给出三档斩味；悬停和键盘提示显示各色段数值、最高斩味，不只靠颜色辨认。
- 数据缺失显示“未收录”，不画成零。源数据库斩味单位需要与上游校准，未校准前不能把储存段长宣称为实际可攻击次数。
- 弓、轻弩、重弩使用专属列：蓄力／瓶，速射／装填／反动等；不能展示不存在的斩味。铳枪炮击、盾斧／斩击斧瓶型、笛音符等支持类型专属列。

后续可以增加 2–3 把武器固定比较，但首版优先把同屏表格与正确的斩味比例做好。

## 6. 合成路线必须直接回答“接下来做什么”

右侧检查器首先显示当前武器性能，其次显示“从哪来”和“去哪里”，最后才是背景说明。

- 「从上一级强化」：明确来源武器、这一步的素材数量与费用。
- 「直接生产」：存在时单列，与强化配方互斥选择，不能把两个配方相加。
- 「继续派生」：列出下一节点，并支持定位。
- 「路线材料」：用户明确设置起点与目标后，沿真实路径累计材料和费用。默认起点不能暗示用户已经拥有某把武器。
- 多种生产配方分别展示；素材点数类保留“需要 N 点”及可选贡献素材，不自动选某个素材冒充必需品。
- 点击素材显示获取来源，继续点击任务显示目标、地图和报酬。保留完整返回路径。
- 本阶段没有库存功能时，只标“路线需求”，不能标“还缺多少”。

## 7. 防具：围绕技能贡献与替换价值展示

防具使用独立的 ArmorBrowser / ArmorDetail，不继续复用武器或素材的通用数值卡片。其核心问题是“这件装备提供什么技能、能放多少珠子、强化后防御如何、是否适合替换当前选项”。

视觉层次：

- 标题区紧凑呈现中文名、部位、剑士／射手／通用、性别限制和稀有度。类别图标仅作为识别，不放大成占据主视觉的伪外观图。
- 第一层突出技能点与插槽。技能树名和正负点数对齐，名称可跳转查看发动阈值与效果。单件“攻击 +3”必须标为技能点贡献，不能误写成已经发动“攻击力提升”。
- 防御写成一条自然的强化信息，例如“初始 20 → 满强化 100”，并显示净提升；此处数字仅作布局示意。数据库目前只有端点时只呈现端点，不编造中间等级、强化材料或费用。
- 五种耐性排成一行：火、水、雷、冰、龙各有固定位置、图标、正负号与数值。负值通过柔和的风险色辅助识别，仍保留文字和符号；0 值弱化。默认不用雷达图，避免小幅数值差被面积夸大。
- 同系列五部位与生产材料放在下一层。材料默认可见，英文风味说明保持折叠。普通信息不再逐块堆相同的圆角大卡片。

列表与筛选：

1. 支持“按部位／按套装”两种入口。按部位使用头、胴、腕、腰、脚明确切换；筛选剑士／射手时保留符合条件的通用件。
2. 列表直接展示防御范围、插槽和技能点摘要。存在技能筛选时把命中的技能置于首位，并明确显示其点数；不能仅显示防御、迫使用户逐件点开。
3. 插槽用实际插槽数量的清晰图形并附“2 孔”等文字提示；无孔标“无孔”，不让三个空圆同时承担“未占用”和“不存在”两种含义。
4. 套装入口按数据库 armor_families 的五个部位 ID 与 armor.family 关系核对关联，不能按名字相似度拼套装。混合适用类型、特殊部位和缺件需要核实后展示，不自动补齐。
5. 点击其他部位只切换选择，保留该套装与滚动上下文。查看素材、技能后返回也恢复原位置。

比较体验：

- 提供“设为比较基准”，固定一件防具后浏览同部位候选。显示技能点、插槽、初始／满强化防御和耐性的逐项差值。
- 比较必须使用相同强化条件；剑士／射手或适用限制不兼容时标明原因，不给出误导的优劣排名。
- 防御上升不能自动判定“更好”：技能损失、孔位变化和负耐性同样显眼。不输出没有配装上下文的综合评分。
- 套装摘要可以汇总五件的技能点、孔位、防御与耐性；发动技能按 skills.required_skill_tree_points 的实际阈值计算，不能假设所有技能都在 +10／+15／+20 发动。汇总范围明确标为“这五件防具”，不隐含武器、珠子与护石。
- 特殊技能、缺失字段或未验证的套装规则不能默认为 0 或普通相加；未经核实的发动推导暂不展示结论。

新增验收：同部位列表无需打开详情就能比较技能与孔位；初始／满强化不混用；技能点与发动效果不混淆；五耐性在深浅模式及非颜色识别下都可读；缺件、长名称、负技能点、无孔与通用装备各有明确状态。防具体验与武器专用界面纳入同一次重构验收。

## 8. 汉化按用户任务链验收

重新统计实际合并词典后，中文名称覆盖现状：

| 数据类别 | 有中文名 | 总数 | 覆盖率 |
|---|---:|---:|---:|
| 普通道具／素材 | 270 | 2,624 | 10.3% |
| 素材点数类别 | 0 | 277 | 0% |
| 装饰品 | 242 | 242 | 100% |
| 任务名称 | 174 | 1,355 | 12.8% |
| 随从武器 | 0 | 495 | 0% |
| 随从防具 | 0 | 1,001 | 0% |

这里统计的是“当前显示名含中文”，不是翻译正确率，也不代表描述、目标、副任务和条件全部完成。任务目标即使含有中文动词，也可能残留英文实体，必须另外审计。

汉化流程：

1. 统一中文名称记录，以稳定实体 ID 关联，保存原文、首选中文、已核实别名、来源、审校状态和版本。列表、树、配方、掉落、任务报酬统一调用，不能每处各翻一次。
2. 普通物品优先使用已有社区中文资料对齐。核对实体关联与来源，不能只靠“怪物前缀 + 部位后缀”猜名，尤其要区分厚鳞、天鳞、刚翼、天壳等。
3. 任务按村／集会所、上下位／G位、星级、地图、主要目标、出现怪物等多字段交叉匹配；跨 XX/GU 版本的事件与联动任务单独核对，不按相邻 ID 硬套。
4. 区分社区既有译名与本项目审校译名，均不能冒称官方；无法确定时明确列入待核实清单。中文目标摘要可以先帮助理解，但不能冒充已经核实的任务标题。
5. 主目标、副目标、地图、关键／紧急标记、掉落条件、报酬栏、素材类别和帮助文本一并汉化。建立术语表，避免“斩击斧／盾斧”等混淆再次发生。
6. 搜索索引同步收录中英文与已核实别名，译名更正后旧别名仍可找到正确条目。
7. 生成独立覆盖报告和待译清单；既检查整库，也检查“热门武器 → 素材 → 获取任务 → 报酬”实际链路。随机复核之外，还要覆盖同名、近似名、特殊任务与版本差异。

交付门槛：以全量普通道具／素材名称、素材点数类别、任务可读信息为目标；不再凭增加几百个词条宣布中文完成。任何未核实项目必须数量明确、可定位；版本报告分别列出名称、目标、副任务、条件和描述的覆盖情况。描述性风味文本可以后排，行动所需信息不能后排。

## 9. 验收与实现顺序

性能数字是拟定验收目标，尚未实现；在当前这台 Mac、Release 构建、完整数据库上记录冷／热状态与 p50/p95。

| 验收项 | 目标 |
|---|---|
| 输入与光标 | 常见输入即时响应，主线程每次输入相关工作争取小于 5 ms |
| 搜索首批结果 | 停止输入后 p95 ≤ 250 ms，包含输入合并等待 |
| 大量结果滚动 | 以本机屏幕刷新率为基准测帧时间，不出现重复的明显卡顿 |
| 树节点切换 | 已缓存详情 p95 ≤ 100 ms，树不重置 |
| 连续输入与取消 | 100 次混合输入流程无持续挂起、无过期结果覆盖 |
| 中文输入法 | 拼音组词、选词、退格、连续候选均不丢字／抢焦点 |
| 返回上下文 | 武器 → 素材 → 任务 → 连续后退，恢复原条件和位置 |
| 派生准确性 | 787 棵树的边、可生产节点、最终节点与数据库一致 |
| 斩味 | 列表／详情一致；不同武器同尺度；近战与远程区别正确 |
| 汉化 | 发布逐类、逐字段覆盖报告，未核实项显式列出 |

实施顺序：

1. 搜索止血与现场定位：加输入／筛选／结果提交／布局测量点；分离查询状态和导航状态，异步索引、取消与合并刷新；先通过中文输入和大量结果测试。
2. 构建武器与防具各自的数据模型和界面：武器完成 14 类导航、稳定树索引、列内斩味和上下文历史；防具完成技能／孔位摘要、强化防御、五耐性、套装关联及同部位比较。先用最大树、长名称与特殊防具验证，再覆盖全量数据。
3. 在界面重构过程中持续准备中文数据，发布前跑通完整中文查询链。任务与素材是本次重构的交付条件，不推给装饰优化之后。
4. 验收素材路线、直接生产与强化分离、特殊武器字段。完成真实键鼠与中文输入法操作检查，再发布构建。

自动配装、逐件装备外观、复杂动画排在以上项目之后。下一版成功的标准是“找得到、看得懂、点得通、回得去、打字不卡”，不是新增了多少面板。
